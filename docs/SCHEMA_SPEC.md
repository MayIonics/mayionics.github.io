# MayIonics D1 Schema Specification

## Scope

This document defines the P2 database contract for the MayIonics V1 commerce system. The schema is implemented by `migrations/0001_initial_commerce.sql` and is designed for Cloudflare D1 / SQLite.

P2 defines storage only. No Worker routes, provider calls, database deployment, or production commerce activation are part of this phase.

## Core Invariants

- Monetary values are integer cents.
- IDs are application-generated text identifiers.
- Timestamps are ISO-8601 text generated by application code.
- Product price and inventory are authoritative server-side values in later phases.
- Historical order items snapshot title and price at purchase time.
- Provider payment IDs are unique within each provider to support idempotent reconciliation.
- Product reservations have explicit expiry and lifecycle state.
- Initial migrations are append-only; destructive schema changes require a later explicit migration and review.

## Tables

### `products`

Stores sellable product data and package metadata needed later for shipping-rate calculation.

Lifecycle: `ACTIVE`, `RESERVED`, `SOLD`, `HIDDEN`.

Condition values: `NEW`, `OPEN_BOX`, `PRE_OWNED`.

`image_data` stores serialized image references/metadata, not image binary data.

### `orders`

Stores customer shipping information, authoritative totals, payment summary state, and fulfillment state.

Payment state: `PENDING`, `PAID`, `FAILED`, `PARTIALLY_REFUNDED`, `REFUNDED`.

Order lifecycle: `PENDING`, `PAID`, `READY_TO_SHIP`, `SHIPPED`, `DELIVERED`, `CANCELLED`, `REFUNDED`.

### `order_items`

Stores immutable purchase snapshots. `product_title`, `unit_price_cents`, and `line_total_cents` preserve the order record if the catalog item changes later.

### `payments`

Provider-neutral payment ledger for Stripe and PayPal. `(provider, provider_payment_id)` is unique so replayed callbacks or webhook reconciliation cannot silently create duplicate provider identities.

Payment lifecycle: `PENDING`, `SUCCEEDED`, `FAILED`, `PARTIALLY_REFUNDED`, `REFUNDED`.

P2 does not yet model separate refund rows. Refund modeling will be reviewed when the payment/refund lifecycle is implemented so the schema is not expanded before requirements are concrete.

### `shipments`

Stores EasyPost shipment/rate identifiers, carrier/service, cost, tracking number, label reference, and fulfillment state.

Lifecycle: `PENDING`, `LABEL_CREATED`, `IN_TRANSIT`, `DELIVERED`, `CANCELLED`, `ERROR`.

A populated label record does not itself prove payment; later application logic must enforce that postage is purchased only for eligible paid orders.

### `product_reservations`

Stores temporary inventory holds used later to protect limited and one-off inventory during checkout.

Lifecycle: `ACTIVE`, `CONSUMED`, `RELEASED`, `EXPIRED`.

`reserved_quantity` permits future products with quantity greater than one. The database intentionally does not impose a one-active-reservation-per-product unique constraint because that would incorrectly prevent multiple reservations when inventory quantity exceeds one. Later Worker code must perform inventory/reservation changes atomically.

## Foreign-Key Policy

Commerce history is preserved with restrictive deletion behavior for products, orders, order items, payments, and shipments. Reservation `order_id` may become null if an associated temporary order is removed, while the reservation audit record remains.

Permanent catalog deletion is not required for V1; products can be marked `HIDDEN`.

## Indexing

P2 creates indexes for:

- product status / recency;
- category / status;
- featured products;
- order customer / recency;
- order status;
- order-item order/product lookups;
- payment order/status lookups;
- shipment order/tracking lookups;
- reservation product/status, expiry, and order lookups.

Indexes can be refined later using observed query patterns; P2 avoids speculative analytics indexes.

## Security Boundary

The browser will never access D1 directly. A later Cloudflare Worker will validate requests and remain authoritative for price, inventory, totals, shipping, payment state, and fulfillment transitions.

No provider secrets belong in migrations or schema documentation.
